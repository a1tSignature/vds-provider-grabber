# vds-provider-grabber

Каталог VDS/VPS хостинг-провайдеров: провайдеры, их юридическая информация и принимаемые способы
оплаты, локации серверов, тарифы с историей цен в режиме «только добавление» и зафиксированным
эквивалентом в USD, курсы валют, авторизация (JWT + bcrypt, на основе ролей), а также API чтения
и поиска по всему этому.

## Чего нет в этом инкременте

- **Краулер и discovery по умолчанию выключены.** Пока не заданы `VDS_CRAWLER_ENABLED=true` и
  `VDS_DISCOVERY_ENABLED=true`, сервис не обращается ни к одному чужому сайту и ни к одному
  поисковому API: каждая строка попадает через write API (или, для локальной разработки, через
  `dev-seed.sql`). Как их включить — в разделе 7.
- **Фронтенд собирается и раздаётся тем же процессом** (см. раздел 8): просмотр каталога для
  всех ролей, формы создания/редактирования и обновление курсов — для `EDITOR`/`ADMIN`.
- **Каталог доступен без входа.** Провайдеры со статусом `CONFIGURED` или `CANDIDATE`, тарифы,
  история цен и справочники доступны всем посетителям; авторизация не меняет видимый набор данных.
- **Изменение и администрирование защищены.** Запись в каталог, формы, управление пользователями,
  курсы валют, краулер и discovery требуют входа и соответствующих ролей.
- **Нет TLS.** Сервис работает по обычному HTTP. См. раздел «Эксплуатационные заметки» ниже о том,
  что это значит перед тем, как выставлять сервис куда-либо.

## Предварительные требования

- JDK 17 или новее (нужен демону Gradle). Само приложение компилируется под JDK 21 и на нём же
  работает.
- Docker (для PostgreSQL через `docker-compose.yml`, а также для `scripts/measure-footprint.sh`).
- Node.js и npm — версия указана в `frontend/.nvmrc` — нужны, чтобы собрать бандл SPA и положить
  его в jar. Без них соберите backend отдельно флагом `-PskipFrontend` (раздел 8).
- Локальный клиент `psql` не требуется — все примеры ниже идут через контейнер PostgreSQL в
  Docker.

`gradle/gradle-daemon-jvm.properties` закрепляет JVM демона Gradle на версии 17; фактическая
компиляция целится в JDK 21 через Kotlin toolchain (`kotlin { jvmToolchain(21) }`), который
автоматически подтягивается резолвером foojay, если локально не найден JDK 21.

**ktlint в этом проекте не настроен** — отдельной Gradle-задачи для линтинга/форматирования нет.

## 0. Быстрый старт: весь проект в Docker

Нужен только Docker — JDK и Node ставить не обязательно: `Dockerfile` сам собирает фронтенд и
fat jar.

```bash
docker compose up -d --build --wait   # PostgreSQL + приложение (API и SPA) на http://localhost:8080
docker compose run --rm seed          # необязательно: тестовые данные из dev-seed.sql (раздел 5)
docker compose run --rm catalog       # необязательно: каталог из catalog-seed/catalog-dump.sql
```

Откройте <http://localhost:8080> и войдите bootstrap-администратором (раздел 4). Логин и пароль
берутся из `VDS_BOOTSTRAP_ADMIN_USERNAME`/`VDS_BOOTSTRAP_ADMIN_PASSWORD` в `.env` рядом с
`docker-compose.yml`, если он есть, иначе — `admin` / `admin-local-dev`. Bootstrap срабатывает
только на пустой таблице пользователей: если volume уже содержит пользователей, действуют они.

| Сервис | Как запустить | Что делает |
|---|---|---|
| `postgres` | по умолчанию | PostgreSQL 17 на `localhost:${VDS_DB_PORT:-5432}`, volume `postgres-data` |
| `app` | по умолчанию | приложение на `localhost:${VDS_APP_PORT:-8080}`; healthcheck — `/health/ready` |
| `seed` | `docker compose run --rm seed` | применяет `dev-seed.sql` после миграций; если провайдеры уже есть — ничего не делает |
| `catalog` | `docker compose run --rm catalog` | загружает `catalog-seed/catalog-dump.sql` (не коммитится) после миграций; если провайдеры уже есть — ничего не делает |
| `frontend` | `docker compose --profile dev up -d` | Vite dev server с hot reload на <http://localhost:5173>, проксирует API в `app` |

Compose читает `.env` только для подстановки переменных из таблицы выше и
`VDS_DB_NAME`/`VDS_DB_USER`/`VDS_DB_PASSWORD`/`VDS_JWT_SECRET`/`VDS_BOOTSTRAP_ADMIN_*`. В
контейнер `app` не передаётся ни одна переменная краулера и discovery, поэтому оба выключены,
что бы ни стояло в `.env`; `VDS_DB_URL` из `.env` тоже игнорируется — контейнер ходит в
`postgres` по имени сервиса.

Пересобрать после изменений в коде — `docker compose up -d --build --wait`; начать с пустой
базы — `docker compose down -v`.

## 1. Запуск PostgreSQL (для запуска jar с хоста)

```bash
docker compose up -d postgres
```

Это поднимает PostgreSQL 17 на `localhost:5432` с постоянным volume. Если поднят и сервис `app`,
остановите его (`docker compose stop app`), чтобы jar с хоста мог занять порт 8080. Миграции Flyway
выполняются автоматически при следующем запуске приложения (см. ниже) — отдельной команды
«migrate» не существует.

## 2. Конфигурация (переменные окружения)

Вся конфигурация задаётся через переменные окружения и проверяется при старте по принципу
fail-fast в `config/AppConfig.kt`: отсутствующая или некорректная переменная приводит к одной
строке лога с именами всех проблемных переменных и завершению процесса с ненулевым кодом *до*
того, как произойдёт что-либо ещё (без попытки подключения к БД, без привязки HTTP-порта).

| Переменная | Обязательна | По умолчанию | Валидация |
|---|---|---|---|
| `VDS_DB_URL` | да | — | не пустая (JDBC URL, например `jdbc:postgresql://localhost:5432/vds`) |
| `VDS_DB_USER` | да | — | не пустая |
| `VDS_DB_PASSWORD` | да | — | не пустая |
| `VDS_DB_POOL_MAX` | нет | `5` | положительное целое число |
| `VDS_DB_POOL_MIN_IDLE` | нет | `1` | ноль или больше |
| `VDS_DB_CONNECTION_TIMEOUT_MS` | нет | `5000` | положительное целое число |
| `VDS_DB_LEAK_DETECTION_MS` | нет | `30000` | ноль или больше |
| `VDS_HTTP_PORT` | нет | `8080` | целое число от 1 до 65535 |
| `VDS_JWT_SECRET` | да | — | не менее **32 символов** |
| `VDS_JWT_TTL_HOURS` | нет | `24` | положительное целое число |
| `VDS_FX_API_URL` | нет | `https://open.er-api.com/v6/latest/USD` | абсолютный URL `http`/`https` |
| `VDS_FX_API_KEY` | нет | *(нет)* | — |
| `VDS_FX_REFRESH_HOURS` | нет | `12` | положительное целое число |
| `VDS_BOOTSTRAP_ADMIN_USERNAME` | нет* | *(нет)* | требуется вместе с паролем ниже, либо не задаётся вовсе |
| `VDS_BOOTSTRAP_ADMIN_PASSWORD` | нет* | *(нет)* | требуется вместе с именем пользователя выше; **от 12 символов и не более 72 байт UTF-8** (собственное ограничение bcrypt на длину входных данных) |
| `VDS_CORS_ALLOWED_ORIGINS` | нет | *(пусто)* | список через запятую; **пустое значение означает полное отсутствие кросс-доменного доступа** — CORS включается явно, а не разрешён по умолчанию |
| `VDS_HTTP_TRUST_FORWARDED_FOR` | нет | `false` | `true`/`false`; `true` — троттлинг входа берёт адрес клиента из последней записи `X-Forwarded-For`. Включайте **только** если до приложения можно достучаться исключительно через обратный прокси, перезаписывающий этот заголовок (раздел 9) |

\* `VDS_BOOTSTRAP_ADMIN_USERNAME`/`VDS_BOOTSTRAP_ADMIN_PASSWORD` — это пара **«всё или ничего»**:
задать только одну из них — ошибка конфигурации.

Переменные краулера (`VDS_CRAWLER_*`) и discovery (`VDS_DISCOVERY_*`) описаны в разделе 7.
Сервис не читает `VDS_ENRICH_*`: их читает отдельный процесс обогащения (раздел 7.9).

## 4. Bootstrap-администратор / первый вход

Эндпоинта самостоятельной регистрации **не существует**. Самый первый пользователь создаётся
самим приложением, один раз, когда таблица `app_user` пуста:

- Если заданы `VDS_BOOTSTRAP_ADMIN_USERNAME`/`VDS_BOOTSTRAP_ADMIN_PASSWORD` **и** таблица
  пользователей пуста, этот пользователь создаётся с ролью `ADMIN`, и строка лога уровня `WARN`
  напоминает сменить пароль, прежде чем полагаться на него для чего-то реального.
- Если таблица пользователей пуста, а эти две переменные **не заданы**, сервис всё равно
  запускается (миграции всё равно выполняются), пишет строку лога `WARN` с просьбой их задать, и
  API остаётся фактически неработоспособным, пока не появится администратор (каждый защищённый
  маршрут требует роль).
- При каждом последующем запуске, если пользователи уже есть, эти две переменные ничего не
  делают — шаг bootstrap превращается в no-op; их можно безопасно держать в окружении процесса
  сколько угодно.

После этого войдите через:

```bash
curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"change-me-after-first-login"}'
```

и используйте полученный `token` как `Authorization: Bearer <token>` для всех остальных
эндпоинтов. Новые пользователи, помимо bootstrap-администратора, создаются через
`POST /api/v1/admin/users` существующим пользователем с ролью `ADMIN`.

## 5. Тестовые данные (dev seed)

`src/main/resources/db/dev-seed.sql` — демонстрационные данные для локальной разработки:
6 провайдеров, 24 тарифа с ценами `MONTHLY`, юридическая информация, способы оплаты и локации в
8 странах, а также несколько намеренных граничных случаев (тариф, закончившийся на складе,
снятый с продажи тариф, тариф с ценой в валюте, для которой нет учтённого курса, и тариф с
закрытой строкой цены перед текущей).

Он применяется **вручную**, Flyway его никогда не трогает — он лежит в
`src/main/resources/db/`, на один уровень выше `db/migration/`, специально для того, чтобы
сканирование миграций Flyway (`classpath:db/migration`) его не видело. Он **не повторно
применим**: он рассчитан на только что смигрированный, полностью пустой каталог (собственная
миграция `V1` от Flyway сидирует только 3 роли) и завершится с ошибкой нарушения уникальных
ограничений при повторном применении. Чтобы вернуться в такое состояние, пересоздайте базу
данных, например:

```bash
docker compose down -v && docker compose up -d postgres
```

При запуске через Docker (раздел 0) достаточно `docker compose run --rm seed`: сервис дождётся
готовности приложения (значит, и миграций) и пропустит seed, если провайдеры уже есть. Вручную —
через контейнер PostgreSQL в Docker (локального `psql` нет):

```bash
docker compose exec -T postgres psql -U vds -d vds < src/main/resources/db/dev-seed.sql
```

Выполняйте это только *после* того, как схема была хотя бы раз смигрирована (т.е. после того,
как приложение хотя бы раз успешно запустилось против этой базы данных).

## 6. Измерение потребления памяти и времени запуска

```bash
./gradlew shadowJar
docker compose up -d postgres                                             # если ещё не запущено
docker compose exec -T postgres psql -U vds -d vds < src/main/resources/db/dev-seed.sql  # если ещё не применено
./scripts/measure-footprint.sh
```

Скрипт запускает fat jar в контейнере, измеряет холодный старт (время до первого `200` от
`GET /health/ready`) и RSS после фиксированной нагрузки запросов к каталогу, печатает оба числа
и завершается с ненулевым кодом, если заданный в скрипте бюджет превышен. Всегда удаляет
запущенный им контейнер, в том числе при неудаче.

Профиль `./scripts/measure-footprint.sh --crawler` дополнительно измеряет сервис с включённым
краулером, а `./scripts/measure-footprint.sh --discovery` — с включённым discovery: простой, пик
во время прохода, пик во время обхода декларативного источника и пик при их совпадении. Ни один
профиль не обращается к настоящему поисковому API и не тратит кредиты.

Профиль `./scripts/measure-footprint.sh --enrich` измеряет **два процесса**: сервис и рядом с ним
процесс обогащения (раздел 7.9), на настоящих сохранённых страницах. Что нужно дополнительно:

- сохранённый прогон прототипа в `~/.vds-real-run/enrich-prototype-run6` (или в каталоге из
  `VDS_ENRICH_REPLAY_DIR`): `results.json` и `pages/<slug>` для 12 сайтов (fornex-com не нужен).
  Без них скрипт останавливается с ошибкой; синтетических страниц нет;
- jar, собранный **с фронтендом** (`./gradlew shadowJar`, без `-PskipFrontend`), и
  `scripts/enrich-launch.sh`: процесс запускается только через обёртку.

Скрипт поднимает `scripts/enrich-replay-server.py` для каждого сайта на портах 18101–18112 хоста и
меряет сервис без обогащения под той же нагрузкой (50 запросов к API плюс SPA: `/`, `/index.html` и
все `/assets/…`, 20 раз). Затем он создаёт 50 провайдеров-кандидатов: 5 пачек по 10 разных сайтов,
в каждой hostinger-com (страница 1,6 МБ) и nuxt-cloud (SPA). Все прочие провайдеры, которые были бы
«к сроку», он помечает `NOTHING_FOUND` и печатает их число, чтобы очередь состояла ровно из этих 50.
Процесс обогащения запускается в отдельном контейнере с теми же образом и флагами JVM
(плюс `-Xlog:gc:stdout`). Каждые 200 мс снимаются RSS процесса и RSS сервиса, раз в секунду — память
PostgreSQL как сумма Pss его процессов (без двойного счёта общей памяти). После завершения процесса
нагрузка повторяется, а созданные провайдеры удаляются. Один режим идёт **25–50 минут**.

- **Режим A (drain)** — одна JVM на все 5 пачек. Таблица по пачкам: пик процесса, `rssMb` в конце
  пачки, занятость кучи после Full GC, длительность. Проходит, если рост `rssMb` от пачки 2 к
  последней ≤ 15 МБ, куча после Full GC выросла ≤ 8 МБ (или падает) и **сумма пиков сервиса,
  процесса и PostgreSQL ≤ 700 МБ**.
- **Режим B (per-batch)** — только если A не прошёл: новая JVM на каждую пачку. Проходит, если сумма
  с наибольшим пиком одной JVM ≤ 700 МБ.
- Пик сервиса печатается рядом с ориентиром 300 МБ, но не решает. Строка «worst case» —
  справочная: 300 МБ сервиса (как если бы одновременно шёл прогон краулера тарифов) плюс пики
  процесса и PostgreSQL.

Последняя строка — `MODE: drain` или `MODE: per-batch` (код 0), либо `STOP` (ненулевой код). От
неё зависит `VDS_ENRICH_BATCHES_PER_JVM` стенда. Числа печатаются, только если все 50 провайдеров
этого режима закончились `SUCCESS` или `NOTHING_FOUND`, у копий Hostinger есть юрлицо, у nuxt-cloud
— способ оплаты, а помеченных провайдеров процесс не тронул. Иначе скрипт пишет `NOT MEASURED` и
завершается с ненулевым кодом. Флаги, размер пачки, лимиты, паузу, нагрузку и страницы ради
прохождения не меняют: решение принимает владелец (ADR vds-002-01).

## 7. Discovery: поиск новых провайдеров и декларативные источники

Discovery состоит из двух независимых частей:

- **Проход discovery** ищет в интернете сайты, похожие на VPS-провайдеров, и заводит для каждого
  скрытую запись-кандидат. Страницы кандидата он не открывает и тарифы не собирает.
- **Декларативный источник** — JSON-файл, который описывает, как собрать данные одного
  провайдера с одной страницы. Его обходит краулер, как и скомпилированный адаптер.

### 7.1. Что нужно от краулера

Discovery работает поверх краулера. При `VDS_DISCOVERY_ENABLED=true` и
`VDS_CRAWLER_ENABLED=false` сервис стартует, пишет `WARN`, не выполняет ни одного прохода, а
эндпоинты discovery отвечают `503`.

Краулер пишет в каталог через тот же HTTP API под отдельной учётной записью. Создайте её заранее
через `POST /api/v1/admin/users` с ролью `EDITOR`.

| Переменная | Обязательна | По умолчанию | Валидация |
|---|---|---|---|
| `VDS_CRAWLER_ENABLED` | нет | `false` | `true`/`false` |
| `VDS_CRAWLER_USERNAME` | при включённом краулере | — | не пустая |
| `VDS_CRAWLER_PASSWORD` | при включённом краулере | — | не пустая |
| `VDS_CRAWLER_API_BASE_URL` | нет | `http://127.0.0.1:8080` | абсолютный URL `http`/`https`; должен указывать на этот же сервис |
| `VDS_CRAWLER_ADAPTERS` | нет | *(пусто)* | id через запятую; неизвестный id — ошибка старта. Пустое значение выбирает все декларативные источники с `"enabled": true` |
| `VDS_CRAWLER_INTERVAL_HOURS` | нет | `24` | положительное целое число |
| `VDS_CRAWLER_INITIAL_DELAY_MINUTES` | нет | `10` | положительное целое число |
| `VDS_CRAWLER_HOST_DELAY_MS` | нет | `2000` | положительное целое число; пауза между запросами к одному хосту |
| `VDS_CRAWLER_RESPECT_ROBOTS` | нет | `true` | `true`/`false` |
| `VDS_CRAWLER_CONTACT_URL` | нет | *(нет)* | абсолютный URL; попадает в `User-Agent`, чтобы владелец сайта мог с вами связаться |
| `VDS_CRAWLER_DRY_RUN_DEFAULT` | нет | `false` | `true`/`false` |

Остальные переменные `VDS_CRAWLER_*` (таймауты, лимит размера страницы, свой `User-Agent`, порог
«нет в наличии») имеют рабочие значения по умолчанию; они перечислены в `config/AppConfig.kt`.
Эндпоинты `/api/v1/admin/crawl/**` описаны в `openapi.yaml`.

### 7.2. Переменные discovery

Пока `VDS_DISCOVERY_ENABLED=false`, ни одно значение `VDS_DISCOVERY_*` не может помешать старту:
некорректное значение даёт строку `WARN` и заменяется значением по умолчанию.

| Переменная | Обязательна | По умолчанию | Валидация |
|---|---|---|---|

### 7.3. Список запрещённых доменов (denylist)

Поиск по словам вроде «vps hosting» в основном возвращает не провайдеров, а обзорные сайты,
форумы, маркетплейсы, соцсети и документацию. Denylist отсекает их до создания кандидата.

- Встроенный список лежит в `src/main/resources/discovery/domain-denylist.txt` и входит в jar.
- Свой список задаётся файлом: `VDS_DISCOVERY_DOMAIN_DENYLIST_FILE=/etc/vds/denylist.txt`.
  Формат — один домен на строку, `#` начинает комментарий, пустые строки пропускаются, размер
  до 64 КБ.
- **Ваш файл заменяет встроенный список, а не дополняет его.** Скопируйте встроенный файл и
  правьте копию.
- Файл читается один раз при старте: после правки перезапустите сервис. Отсутствующий или
  слишком большой файл при включённом discovery — ошибка старта.
- Запись блокирует и все свои поддомены: `reddit.com` блокирует `old.reddit.com`. Регистр,
  `www.` и точка в конце роли не играют. Запись, которая не является доменом, пропускается со
  строкой `WARN`.
- Пустой файл или пустое значение `VDS_DISCOVERY_DOMAIN_DENYLIST` отключают denylist совсем.
- **Порядок записей важен.** Первые 150 записей (лимит Tavily) уходят в запрос как
  `exclude_domains`: такие сайты не занимают места в выдаче, и с того же кредита приходит больше
  провайдеров. Кредит списывается за запрос в любом случае. Остальные записи отсекаются только у
  нас, поэтому самые частые обзорники и агрегаторы держите в начале файла.

Помимо denylist, без настройки отсекаются страницы-подборки: рейтинги и сравнения по заголовку
(«top 10», «5 best», «рейтинг», «vergleich», «classement», «comparativa», «ranking» и т. п.) и по
пути URL (`/tag/`, `/top/`, `/reviews`, `/comparison/` и т. п.). В сводке прохода они считаются
как `LISTICLE`. Фильтр намеренно узкий: у самих хостеров много статей «best …» и руководств, и
более широкое правило выбрасывало бы настоящих провайдеров.

### 7.4. Аккаунт Tavily и кредиты

Это правила, а не рекомендации: только они гарантируют, что поиск остаётся бесплатным.

- Аккаунт на **бесплатном тарифе, без привязанного способа оплаты и без pay-as-you-go**. Только
  тогда исчерпанный лимит означает отказ в поиске, а не списание денег.
- Бесплатный тариф даёт **1000 кредитов в месяц**; один поиск уровня `basic` стоит **1 кредит**.
  Сервис использует только `basic`.
- Локальный лимит `VDS_DISCOVERY_MAX_CREDITS_PER_MONTH` (по умолчанию 300) ведётся в файле
  `VDS_DISCOVERY_STATE_FILE`. Кредит записывается до запроса, а не после. Если файл не читается,
  поиск не выполняется вовсе.
- Перед проходом сервис сверяется с остатком, который сообщает сам Tavily, и берёт более
  строгую из двух цифр.
- Ответ `429` считается сбоем одного запроса: проход переходит к следующему. Исчерпанная квота
  или отвергнутый ключ завершают проход.

- **Число с подписью.** Из значения берётся первое число: `2 vCPU Cores` читается как 2,

- **Размеры с единицами.** Для `ramMb`, `diskGb` и `trafficLimitGb` единица после числа (`MB`,

  1000 ГБ. Если страница пишет число без единицы, укажите её ключом `"unit": "GB"`.
  Запись `2 x 960 GB` (несколько одинаковых дисков) читается как сумма, 1920 ГБ.
- **Константа вместо селектора.** То, что на странице написано один раз или не написано вовсе,
  задаётся значением: `"virtualization": {"value": "KVM"}`, `"ipv4Count": {"value": "1"}`,
  `"provider": {"name": {"value": "Example Host"}, ...}`. Цену константой задать нельзя.
- **Цена.** Берётся число рядом с символом валюты, после него или перед ним: `From $8.50 /month`
  читается как 8.50, `6.00 € −37%` — как 6.00. Если рядом с символом числа нет, берётся первое
  число после символа, затем перед ним.
- **Берётся текущая (акционная) цена.** Зачёркнутые суммы внутри выбранного элемента — `del`, `s`,
  `strike` или класс/стиль с `line-through`, `strike`, `old-price` — пропускаются: из
  `<del>$83</del> $66` читается 66. Если старая цена выделена без такой разметки (например,
  хэшированными CSS-классами), выберите селектором элемент с текущей ценой. Ключ цены
  `"regularPrice": true` включает обратное: читать зачёркнутую обычную цену — внутри выбранного
  элемента или рядом с ним в пределах строки тарифа.
- **Значения перечислений по вхождению.** В `values` у `diskType`, `virtualization`, `inStock` и
  `ipv6Supported` сначала ищется точное совпадение текста, затем самый длинный ключ, который в
  тексте встречается: `200 GB NVMe` с картой `{"NVMe": "NVME", "SSD": "SSD"}` даёт `NVME`.
- **Одинаковые названия тарифов.** `"disambiguateNames": true` в секции `tariffs` добавляет к
  совпадающим названиям (и `externalId`) префикс из характеристики, которая их различает: диск,
  RAM, vCPU или их сочетание, например `150 GB disk · 16 GB RAM`. По умолчанию выключено: чаще
  всего одинаковые названия означают селектор, который в каждой строке находит один и тот же
  элемент.

Нужную строку в списке характеристик удобно выбирать по тексту: `li:contains(GB RAM)`.

Источник читает только то, что есть в HTML страницы. Тарифы, которые сайт подгружает скриптами,
и сайты, отвечающие `403` автоматическим клиентам, этим форматом завести нельзя.

Как добавить и включить источник:

1. Положите файл `*.json` в каталог `VDS_DISCOVERY_SOURCES_DIR`. Ограничения: до 64 КБ на файл,
   до `VDS_DISCOVERY_MAX_SOURCES` файлов, обычный файл (символическая ссылка отвергается),
   CSS-селекторы без обратной косой черты (вместо `.md\:flex` пишите `[class*=md:flex]`).
2. Поставьте `"enabled": true` **в самом файле**.
3. **Перезапустите сервис.** Файлы читаются только при старте; горячей перезагрузки нет, и это
   сделано намеренно.
4. Проверьте результат: `GET /api/v1/admin/discovery/sources` показывает загруженные источники
   и файлы, которые загрузить не удалось, с текстом ошибки. Другого способа убедиться, что
   перезапуск подхватил файл, нет. Эндпоинт отвечает `503`, пока discovery выключен, хотя сами
   источники читаются при любом включённом краулере.

### 7.6. Запуск вручную

Сначала всегда `dryRun`. Все эндпоинты требуют роль `ADMIN`.

```bash
# обход источника: сначала без записи в каталог
curl -s -X POST http://localhost:8080/api/v1/admin/crawl/run \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"adapterIds":["example-static-declarative"],"dryRun":true}'

# проход discovery: сначала без создания кандидатов
curl -s -X POST http://localhost:8080/api/v1/admin/discovery/run \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"dryRun":true,"maxQueries":1}'

curl -s http://localhost:8080/api/v1/admin/discovery/passes -H "Authorization: Bearer $TOKEN"
```

- **Пробный проход discovery выполняет настоящие поисковые запросы и тратит настоящие
  кредиты.** Он только ничего не пишет в каталог. `maxQueries` ограничивает расход.
- `force: true` снимает только минимальный интервал между проходами, но не месячный лимит.
- Проход и обход не идут одновременно: второй запуск получает `409`.
- Когда набрано `VDS_DISCOVERY_MAX_NEW_CANDIDATES_PER_PASS` кандидатов, проход перестаёт
  искать, чтобы не тратить кредиты. Поэтому `candidatesDeferred` в сводке — нижняя оценка.
- Результат поиска с URL длиннее 2048 символов отклоняется как `MALFORMED_URL`.
- Сводки последних 20 проходов хранятся только в памяти и пропадают при перезапуске.

### 7.7. Кандидаты в каталоге

- Проход создаёт провайдера со статусом `CANDIDATE`. Кандидаты доступны в публичном каталоге вместе
  с настроенными провайдерами; `REJECTED` записи не показываются в каталоге.
- Кандидат становится `CONFIGURED` автоматически после первого успешного обхода, то есть когда
  для него написан и включён источник.
- `REJECTED` ставит только человек: `PUT /api/v1/providers/{id}/system-status`. Это конечное
  состояние, проход не создаст такого кандидата заново.

**Один домен — одна запись.** Дубликаты отсекаются по нормализованному домену. Перед сравнением
служебные и языковые поддомены сворачиваются к родительскому: `docs.`, `kb.`, `wiki.`, `blog.`,
`billing.`, `portal.`, `console.`, `my.`, `cdn.`, `support.`, `help.`, `forum.`, `community.` и
любая двухбуквенная метка (`us.`, `kr.`, `en.`). Так `billing.example.com` и `us.example.com`
становятся `example.com`. Если остаётся голый суффикс вроде `co.uk`, домен не сворачивается.
Поэтому:

- `vps.example.com` и `example.com` — две разные записи (метка `vps` не служебная);
- провайдер, сменивший домен, появится второй записью;
- региональные домены одной компании (`example.com`, `example.ru`) — отдельные записи.

Это выглядит как ошибка, но сделано намеренно: объединение потребовало бы списка публичных
суффиксов и догадок о том, кто кому принадлежит.

### 7.8. Юридическая ответственность

Здесь два разных случая.

**Сбор и публикация тарифов.** Кандидат создаётся по одному результату поиска. Никто не проверял
условия использования его сайта, `robots.txt` и право перепубликовывать его цены. Единственный
человек между находкой и моментом, когда сервис начнёт читать этот сайт и публиковать его
тарифы, — автор файла источника. Включая источник, вы подтверждаете, что прочитали условия
сайта и что сбор и публикация этих данных вам разрешены.

**Обогащение профиля** (раздел 7.9) идёт для каждого провайдера, кроме `REJECTED`, в том числе
для кандидатов, которых ещё не смотрел человек. Основание — ADR `vds-007-adr-02`. Правила:

- `robots.txt` соблюдается всегда (с `*` и `$`);
- честный `User-Agent`; задать `VDS_CRAWLER_CONTACT_URL` рекомендуется;
- никакого обхода анти-бот защиты: такой сайт получает `BLOCKED` и до следующего срока не
  запрашивается;
- не больше 25 страниц на провайдера, пауза между запросами к хосту;
- не чаще раза в `VDS_ENRICH_INTERVAL_HOURS`;
- только собственный сайт провайдера;
- только сведения о провайдере (юрлицо, страна регистрации, способы оплаты, страны серверов), не
  больше 3 фрагментов по 220 символов на значение;
- ничего не показывается вне каталога, закрытого логином; кандидаты скрыты из списка по
  умолчанию.

**Отказ от обогащения:** переведите провайдера в `REJECTED`. Дальше его не обогащают; уже
собранные данные остаются, пока их не удалит человек.

### 7.9. Обогащение профиля провайдера с его сайта

Обогащение — **отдельный короткоживущий процесс**: тот же jar, вторая точка входа
`org.a1tsign.vds.crawler.enrich.EnrichMainKt`. Он не поднимает HTTP-сервер и не ходит в базу.
Процесс входит в API сервиса под аккаунтом `EDITOR`, обрабатывает очередь, пишет результаты через
`PUT /api/v1/providers/{id}/enrichment` и завершается. Прогон краулера тарифов больше не
обогащает.

Для каждого провайдера процесс обходит его собственный сайт: до 25 страниц того же домена (`/`,
страница тарифов, sitemap, страницы оплаты, контактов, условий, дата-центров). Он находит юрлицо,
страну регистрации, способы оплаты и страны серверов и к каждому значению сохраняет доказательства
(URL и фрагмент текста). Сервер применяет правило «ручное побеждает»: значение, которое человек
отредактировал или подтвердил, автоматика не меняет. Способы оплаты и страны только добавляются.
Обогащение никогда не меняет `systemStatus`, так что кандидат от него не становится `CONFIGURED`.
Поисковый API (Tavily) не используется.

Запросы идут с тем же `User-Agent`, паузой между запросами к хосту и лимитом размера, что и у
краулера (те же переменные `VDS_CRAWLER_*`). `robots.txt` соблюдается всегда. Сайт, ответивший
анти-бот проверкой (Cloudflare challenge или страница с одной CAPTCHA), получает `BLOCKED`; обойти
проверку процесс не пытается.

**Очередь.** В неё входят все провайдеры с `systemStatus` `CONFIGURED` или `CANDIDATE`; `REJECTED`
не входит никогда. Провайдер «к сроку», если попыток не было или последняя (любой исход) старше
`VDS_ENRICH_INTERVAL_HOURS`. Сначала идут те, кого ещё не пробовали (по `id`), потом самые давние
попытки. Очередь строится из `GET /api/v1/providers` по полю `enrichmentLastAttemptAt`.

**Пачки.** Процесс берёт пачку из 10 провайдеров и обогащает их по одному, у каждого свой таймаут.
В начале каждой пачки очередь перечитывается, так что новые кандидаты и решения `REJECTED` видны
сразу. Пачки идут, пока очередь не опустеет. Каждого провайдера процесс пробует не больше одного
раза за запуск, и попытка записывается до начала обхода. Результат провайдера уходит на сервер
сразу после его обхода, одной транзакцией. Поэтому сбой теряет только провайдера, который
обрабатывался в этот момент, а следующий запуск продолжит с него. Перед каждым провайдером его
карточка перечитывается: удалённый, ставший `REJECTED` или уже не «к сроку» пропускается без
запроса к сайту.

| Переменная | Обязательна | По умолчанию | Валидация / смысл |
|---|---|---|---|
| `VDS_ENRICH_API_BASE_URL` | нет | `http://127.0.0.1:8080` | абсолютный http(s); API сервиса на той же машине |
| `VDS_ENRICH_USERNAME` / `VDS_ENRICH_PASSWORD` | да | — | аккаунт `EDITOR`; пароль и токен в лог не попадают |
| `VDS_ENRICH_INTERVAL_HOURS` | нет | `720` | положительное целое |
| `VDS_ENRICH_PROVIDER_TIMEOUT_MINUTES` | нет | `4` | положительное целое; при истечении — `TIMEOUT`, найденное не сохраняется |
| `VDS_ENRICH_MAX_PAGES` | нет | `25` | целое от 1 до 50 |
| `VDS_ENRICH_MAX_PAGES_PER_SECTION` | нет | `4` | положительное целое; страниц на первый сегмент пути |
| `VDS_ENRICH_MAX_SITEMAPS` | нет | `4` | положительное целое |
| `VDS_ENRICH_MAX_RUNTIME_MINUTES` | нет | `360` | положительное целое; бюджет одного запуска |
| `VDS_DISCOVERY_SOURCES_DIR` | нет | *(нет)* | каталог источников (7.5): страница тарифов и наблюдаемые адаптером разделы берутся оттуда. Без него — WARN, обход с `/` |
| `VDS_CRAWLER_HOST_DELAY_MS`, `VDS_CRAWLER_USER_AGENT`, `VDS_CRAWLER_CONTACT_URL`, `VDS_CRAWLER_MAX_BODY_BYTES` | нет | как у краулера | те же имена и значения по умолчанию, что у сервиса |

Ошибка в переменной — одна строка ERROR со всеми проблемными именами и выход с кодом `1` до
любого сетевого запроса. `VDS_DB_*` и `VDS_JWT_*` не нужны. Выключить обогащение — значит не
запускать процесс.

Параметры командной строки: `--dry-run` — читает и обходит, но ничего не пишет, а в конце
печатает до 200 строк `ENRICH …` с планируемыми изменениями (их число приблизительное);
`--force` — считает «к сроку» всех из очереди, порядок и правило «раз за запуск» сохраняются;
`--max-batches N` — остановиться после N пачек; `--attempted-file PATH` — файл с id уже
опробованных провайдеров (его ведёт обёртка).

Коды выхода: `0` — очередь пуста (в том числе «ничего не к сроку»); `10` — остановлен
`--max-batches` или бюджетом, а к сроку ещё кто-то остался; `1` — ошибка конфигурации, каталог
недоступен при чтении очереди или аккаунт отвергнут. Любой другой код (`3` от
`ExitOnOutOfMemoryError`, `137` от kill) — падение.

Лог (stdout), каждая строка начинается с `launchId`:

- на провайдера: `enrich provider <slug> id=… systemStatus=… outcome=… durationMs=… pages=…
  valuesApplied=… message=…`;
- на пачку: `enrich batch <N> providers=… outcomes={…} durationMs=… rssMb=…` (`rssMb` из
  `/proc/self/status`; на macOS его нет);
- итог: `enrich launch finished: batches=… attempted=… skipped=… exitReason=… exitCode=…`.

**Локальный запуск.** Сервис запущен на `:8080`, в нём заведён пользователь `EDITOR`:

```bash
./gradlew shadowJar
export VDS_ENRICH_USERNAME=enricher VDS_ENRICH_PASSWORD='…'
export VDS_DISCOVERY_SOURCES_DIR=$PWD/sources
java -cp build/libs/vds-provider-grabber-1.0-SNAPSHOT-all.jar \
  org.a1tsign.vds.crawler.enrich.EnrichMainKt --dry-run
# или через обёртку, с теми же флагами JVM, что на стенде:
VDS_ENRICH_JAR=build/libs/vds-provider-grabber-1.0-SNAPSHOT-all.jar \
  VDS_ENRICH_LOCK_FILE=/tmp/vds-enrich.lock scripts/enrich-launch.sh
```

**Обёртка** `scripts/enrich-launch.sh` — единственный поддерживаемый способ запуска на стенде и в
замере памяти. Она берёт неблокирующий `flock` на `VDS_ENRICH_LOCK_FILE` (по умолчанию
`/var/lock/vds-enrich/lock`): пока идёт предыдущий запуск, новый пишет «previous launch still
running» и выходит с `0`. JVM она запускает с измеренным набором флагов (`-Xmx192m … -XX:+UseSerialGC`).
`VDS_ENRICH_BATCHES_PER_JVM=0` — одна JVM до опустошения очереди, `1` — одна пачка на JVM с
перезапуском, пока JVM выходит с `10`. После падения JVM обёртка перезапускает её не больше 3 раз;
провайдер, на котором она упала, пропускается до следующего запуска. После
`VDS_ENRICH_MAX_RUNTIME_MINUTES` новых JVM не запускается.

**Replay сохранённых страниц.** `scripts/enrich-replay-server.py` раздаёт один сайт из сохранённого
прогона прототипа (`results.json` + `pages/<slug>/NN.html`). Абсолютные ссылки на исходный хост он
переписывает на `http://<хост>.localhost:<порт>`. Только stdlib Python 3:

```bash
python3 -I scripts/enrich-replay-server.py --run-dir ~/.vds-real-run/enrich-prototype-run6 \
  --slug hostinger-com --port 8765
# сайт доступен как http://www.hostinger.com.localhost:8765
```

Чтобы обогатить провайдера с replay, укажите этот origin в `websiteUrl` провайдера и, если нужна
страница тарифов, в `baseUrl` источника того же slug в `VDS_DISCOVERY_SOURCES_DIR`. Затем запустите
процесс с `--force`.

## 8. Фронтенд: сборка и раздача SPA

Один процесс, один порт: бандл `frontend/` (React + TypeScript + Vite) собирается Gradle'ом и
раздаётся тем же Ktor-процессом, что и JSON API — отдельного nginx или второго порта нет, и
`VDS_CORS_ALLOWED_ORIGINS` поэтому может оставаться пустым и в production, и в деве (`vite dev`
проксирует `/api`, `/health`, `/version` на локальный backend, см. `frontend/README.md`).

```bash
./gradlew build            # npm ci + npm run build внутри frontend/, бандл попадает в jar как static/
./gradlew build            # второй прогон без изменений — buildFrontend/syncFrontendDist: UP-TO-DATE
./gradlew build -PskipFrontend   # собрать только backend, без Node/npm; jar без static/, API работает
```

Без флага и без `npm` в `PATH` сборка завершится одной понятной строкой с требуемой версией Node
(см. `frontend/.nvmrc`) и подсказкой про `-PskipFrontend`, а не трассировкой `Exec`.

API никогда не перекрывается SPA: путь с первым сегментом `api`, `health`, `version` или
`openapi.yaml`, не совпавший ни с одним реальным маршрутом, получает `404` в стандартном JSON
конверте (`ApiError`), а не `index.html`. `GET /` и любой непойманный путь (например,
`/providers/42`) отдают `index.html`, чтобы клиентский роутинг SPA работал по прямой ссылке.

## 9. Деплой на стенд

`deploy/stand/` — конфигурация для сервера: Caddy (TLS) → приложение → PostgreSQL, наружу
открыты только порты Caddy. CI публикует multi-arch образ в GHCR после успешной сборки и тестов для
version tag `v*`. Серверу достаточно Docker Compose v2, `openssl` и файлов из `deploy/stand/`;
исходный код и сборочный toolchain на нём не нужны. Пошаговая инструкция — в
[`deploy/stand/README.md`](deploy/stand/README.md).

```bash
cd deploy/stand
./init-env.sh                 # .env из .env.example со случайными паролями и JWT-секретом
$EDITOR .env                  # домен и VDS_IMAGE с опубликованным version tag
docker compose pull
docker compose up -d --wait
```

- **TLS.** Если `VDS_SITE_ADDRESS` — доменное имя, Caddy сам получает и продлевает сертификат
  Let's Encrypt; для этого DNS домена должен указывать на стенд, а порты 80 и 443 — быть доступны
  из интернета. `VDS_SITE_ADDRESS=:80` — обычный HTTP, когда TLS терминирует другой прокси перед
  стендом; тогда троттлинг входа видит адрес этого прокси, а не клиента.
- **Вход.** Логин и пароль администратора — `VDS_BOOTSTRAP_ADMIN_USERNAME`/`..._PASSWORD` из
  `.env`; создаётся при первом старте на пустой базе. Пользователей `EDITOR`/`VIEWER` заводит
  администратор через `POST /api/v1/admin/users`.
- **Что отличается от локального запуска:** секреты обязательны (без них `docker compose`
  откажется стартовать), PostgreSQL наружу не публикуется, `restart: unless-stopped`, лимиты
  памяти (`VDS_APP_MEM_LIMIT`, `VDS_DB_MEM_LIMIT`; heap JVM — 75% лимита), ротация логов Docker
  (5 × 10 МБ), корневая ФС приложения только для чтения, без Linux capabilities, заголовки
  `X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`, сжатие ответов.
- **Краулер и discovery выключены** — их переменные в контейнер не передаются.
- **Обогащение** — сервис `enrich` в профиле `enrich`; `docker compose up` его не запускает. Это
  одноразовый контейнер с тем же образом и точкой входа `/app/enrich-launch.sh` (раздел 7.9). Он
  ходит в `http://app:8080`, а lock лежит в именованном volume `enrich-lock`, общем для всех
  запусков. Один раз заведите для него аккаунт `EDITOR` с паролем `VDS_ENRICH_PASSWORD` из `.env`:

  ```bash
  curl -s -X POST https://$VDS_SITE_ADDRESS/api/v1/admin/users \
    -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
    -d '{"username":"enricher","password":"<VDS_ENRICH_PASSWORD>","roles":["EDITOR"]}'
  docker compose --profile enrich run --rm --no-deps enrich --dry-run   # проверка
  ```

  Расписание — systemd: скопируйте `vds-enrich.service` и `vds-enrich.timer` в
  `/etc/systemd/system/`, поставьте в `WorkingDirectory` путь к этому каталогу и выполните
  `systemctl daemon-reload && systemctl enable --now vds-enrich.timer` (ежедневно около 04:30 UTC,
  со случайной задержкой до 30 минут); лог — `journalctl -u vds-enrich`, неудачный запуск виден в
  `systemctl --failed`. Вместо таймера подойдёт cron; вывод перенаправьте в файл, потому что
  контейнер с `--rm` уносит свой лог Docker с собой:
  `30 4 * * * cd /opt/vds-stand && docker compose --profile enrich run --rm --no-deps enrich >> /var/log/vds-enrich.log 2>&1`.
  Пересечение запусков (таймер, cron, ручной) исключает `flock`. `VDS_ENRICH_BATCHES_PER_JVM` в
  `.env`: `0` — одна JVM на запуск (по умолчанию, по замеру 2026-11-15), `1` — одна пачка на JVM;
  значение выбирает замер памяти (раздел 6). `VDS_ENRICH_MEM_LIMIT` — лимит памяти контейнера (по умолчанию `512m`).
  Остальные `VDS_ENRICH_*` и `VDS_CRAWLER_*` из таблицы раздела 7.9 тоже берутся из `.env`. Чтобы
  процесс знал страницы тарифов, смонтируйте каталог источников в сервис `enrich` (только чтение,
  через `docker-compose.override.yml`) и задайте путь внутри контейнера в `VDS_ENRICH_SOURCES_DIR`;
  без этого каждый сайт обходится с `/`.
- **`.env` не теряйте:** пароль БД из него уже записан в volume; `init-env.sh` не перезапишет
  существующий файл.

Новая версия публикуется командой `git tag v1.2.3 && git push origin v1.2.3`: workflow сначала
собирает и тестирует проект, затем отправляет multi-arch образ `ghcr.io/a1tsign/vds-provider-grabber`
в registry. Для обновления поменяйте закреплённый version tag в `VDS_IMAGE`, создайте backup и
выполните `docker compose pull && docker compose up -d --wait`; миграции Flyway применятся при
старте. Теги выпуска и обновления образа подробнее описаны в `deploy/stand/README.md`.

Резервная копия и восстановление (файлы — в `deploy/stand/backups/`, он в `.gitignore`):

```bash
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc -f /backups/vds-$(date +%F).dump'
docker compose stop app
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists /backups/vds-YYYY-MM-DD.dump'
docker compose start app
```

## Эксплуатационные заметки

- **Логи идут только в stdout.** `CallLogging` никогда не включает заголовок `Authorization`
  или тело запроса в какую-либо строку лога.
- **Сбой Flyway завершает процесс с ненулевым кодом до того, как HTTP-сервер привяжет порт** —
  наполовину смигрированная база данных никогда не обслуживает трафик.
- **SIGTERM** сначала отменяет идущий проход discovery, затем дренирует запросы в полёте до
  10 секунд, останавливает планировщики и идущий обход и закрывает пул соединений. Проходу и
  обходу даётся до 10 секунд на завершение, поэтому остановка может занять около 20 секунд:
  **таймаут остановки контейнера не должен быть меньше** (у Docker по умолчанию он 10 секунд).
- **Не выставляйте этот сервис публично, пока он не стоит за обратным проксом с TLS-терминацией.**
  Он работает по обычному HTTP: bearer-токены и пароли будут пересекать интернет
  незашифрованными. За прокси троттлинг входа по умолчанию видит адрес прокси, а не клиента —
  см. `VDS_HTTP_TRUST_FORWARDED_FOR` (раздел 2) и стенд в разделе 9.
- Корневой `docker-compose.yml` рассчитан на локальный запуск (дефолтный JWT-секрет и пароль
  администратора, открытый порт PostgreSQL); для сервера — `deploy/stand/` (раздел 9). CI
  публикует образы по version tags, но автоматический деплой, плановые бэкапы и тюнинг PostgreSQL
  остаются задачами владельца сервера.
